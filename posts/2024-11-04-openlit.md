Profitant d'une session de R&D avec des collègues, on a voulu tester le SDK [OpenLIT](https://docs.openlit.io), une bibliothèque pour auto-instrumenter les applications à base de LLM. On est allé au plus simple en créant une petite application qui appelle un modèle via [Ollama](https://ollama.com), génère des télémétries et les envoie sur Grafana Cloud.

### Ollama

Ollama est un équivalent de Docker mais pour les LLMs. Ça permet de packager, distribuer des modèles, les build avec des “modelfile” (équivalents de Dockerfiles), et les exécuter localement au travers d'une une API standard. Il y a un [équivalent de DockerHub](https://ollama.com/library) sur lequel on retrouve différents modèles comme Llama, Mistral, Gemma, etc. Comme Docker c’est une archi client-server, avec un CLI, un daemon, et un process par modèle qui tourne.
_Note : il semble que [Cortex](https://cortex.so/) soit sur le même crédo, mais faute d'expertise, on ne saurait préciser ce qui le distingue._

### Setup

Pour simplifier l’installation, on fait tout tourner dans des conteneurs. Pas de prérequis autres que Docker.

* On créer un bridge Docker : `docker network create test_openlit`
* On lance le daemon Ollama : `docker run --detach --rm --volume ollama:/root/.ollama --name ollama --network test_openlit ollama/ollama`
* On pull un modèle : `docker exec --interactive --tty ollama ollama pull llama3.2:1b`
* On créer un fichier de configuration pour le collecteur OpenTelemetry. Dans notre cas on souhaite envoyer logs, traces, et métriques sur Grafana cloud :
  ```yaml
  # config.yaml

  receivers:
    otlp:
      protocols:
        http: # OpenLIT ne supporte pas le gRPC
          endpoint: 0.0.0.0:4318

  exporters:
    otlphttp: # la gateway OTLP Grafana ne supporte pas le gRPC
      endpoint: https://otlp-gateway-prod-eu-west-0.grafana.net/otlp
      headers:
        authorization: <REPLACE_ME>

  processors:
    batch:
      send_batch_size: 100
      send_batch_max_size: 100
      timeout: 3s

  service:
    pipelines:
      traces:
        receivers: [otlp]
        processors: [batch]
        exporters: [otlphttp]
      metrics:
        receivers: [otlp]
        processors: [batch]
        exporters: [otlphttp]
      logs:
        receivers: [otlp]
        processors: [batch]
        exporters: [otlphttp]
  ```
* On lance le collecteur OpenTelemetry : `docker run --detach --rm --volume $PWD/config.yaml:/etc/otelcol/config.yaml --name opentelemetry-collector --network test_openlit otel/opentelemetry-collector`
* Puisqu'OpenLIT est fait pour instrumenter du code, on ne peut pas simplement utiliser la CLI `ollama`. On utilise donc la bibliothèque Python pour interagir avec le daemon :
  ```python
  # main.py

  import openlit
  from ollama import Client

  openlit.init(otlp_endpoint="http://opentelemetry-collector:4318")

  client = Client(host='http://ollama:11434')
  response = client.chat(
    model='llama3.2:1b',
    messages=[{'role': 'user', 'content': 'Hello world.'}]
  )
  print(response['message']['content'])
  ```
* On se place dans un conteneur Python: `docker run --rm --interactive --tty --volume $PWD/main.py:/work/main.py --network=test_openlit python bash`
* Une fois dans le conteneur, on installe les packages nécessaires : `pip install openlit ollama`
* Toujours dans le conteneur, on lance notre programme : `python3 /work/main.py`

### Résultats

On retrouve les données suivantes dans Grafana :

* Une trace par invocation de notre modèle, composée d’une seule span avec 2 events attachés : `gen_ai.content.prompt` contenant le prompt utilisateur, et `gen_ai.content.completion` contenant la réponse du modèle
* Quelques métriques (par exemple `gen_ai_requests_total`, `gen_ai_usage_input_tokens_total`, etc.), qui dans notre cas n’ont pas d’intérêt puisque notre programme s’arrête après chaque invocation, remettant les compteurs à 0
* Pas de logs
* _Note : On peut aussi récupérer des métriques liées au GPU, si on a installé la “NVIDIA Management Library”, ce qui n’est pas le cas sur ma machine_

La première impression est que c'est très pauvre (il n'y a même pas de quoi partager un screenshot), peut être dû à notre cas d’usage trop simpliste. Dans tous les cas, on ne comprend pas comment OpenLIT pourrait avoir plus d'informations puisque seul le client est instrumenté. On doit donc se contenter d’information superficielle: nombre d’appels, latence, nombres de tokens, … Peut être que dans d'autres contextes (pas Ollama), le backend d'inférence peut être instrumenté ?

La prochaine étape consiste à tester la GUI OpenLIT, qui nécessite une base de données Clickhouse et se déploie avec [docker-compose](https://github.com/openlit/openlit/blob/main/docker-compose.yml). À noter : il semble qu'OpenLIT, qui avait démarré comme simple SDK d'auto-instrumentation de LLM, élargit son périmètre et cherche à devenir une plateforme SaaS complète pour gérer des applications de gen AI.
